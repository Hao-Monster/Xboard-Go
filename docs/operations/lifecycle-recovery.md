# 生命周期与开发发布失败恢复

关联：OPS-002；BUG-20261010-02、07、08。以下是恢复边界，不是执行真实恢复的授权。

## 候选失败时保留最新数据

`legacy-parity.yml` 和 lifecycle 的 combined / split backend 升级不再自动恢复预升级数据库快照。候选可能在健康检查完成前接受业务写入，也会启动后台任务。在线快照不能证明其后没有已确认写入；恢复旧库会撤销这些状态。

- 候选激活之前的解析、备份或准备记录失败，不执行候选切换。
- 一旦尝试激活包含 backend 的候选，错误按“可能已触及数据库”处理：停止对应应用/backend，保留当前数据库及 SQLite sidecars、附件、配置和预升级备份，返回失败。停止失败同样返回且记录，不能认定已经停机。
- lifecycle 的停止动作不沿用已取消的调用 context，使用独立的 30 秒上限；不会因收到取消信号而自动恢复旧数据。
- split 仅 frontend/gateway 更新失败仍可回到记录的旧组件组合，不恢复数据库。
- 成功升级的身份、版本和健康门禁不变。状态写入失败也不是成功；候选包含 backend 时仍停止并保留数据。

Legacy parity 在修改配置前写入应用目录的 `.deployment-failed`。同一临界区完成容器、loopback 和公开 HTTPS 域名检查后才移除；这些公开检查现在在 SSH 目标端执行，不代表第三方网络验收。失败或中断保留该标记，下一次自动发布会拒绝执行。预先存在的标记（包括符号链接）不会被覆盖。

## 恢复前的人工决策

1. 先核对 failure marker/journal、运行中的精确镜像与 DSN、停止是否成功、当前数据库/WAL/SHM和备份是否完整。保留现场，不通过删除失败标记反复自动重试。
2. 分清向前修复、兼容的镜像回退、恢复旧快照三种操作。数据库兼容性未知时不要直接启动旧镜像。
3. **显式快照 rollback 会恢复预升级时点，可能丢弃之后的写入或重新处理外部副作用。** 必须先保留当前恢复集并对账，得到对应环境及数据恢复授权。Legacy parity 的预升级备份是 database-only，不能将其称为完整附件/密钥恢复集。
4. `xboard-lifecycle rollback` 接受 `upgraded` 或 `target_failed`，目标容器可以 unhealthy 或 stopped，但必须可辨认、镜像及 DSN仍匹配记录，且备份 manifest有效。容器不存在、部分组件身份不符、journal损坏等情形仍拒绝，不静默猜测目标。
5. 只有经授权的恢复流程核对当前配置、实际版本、数据库及健康一致后，才清除失败标记恢复自动发布。所有共享环境恢复仍经 CI/CD，不在本地直接执行服务端重启、上传或数据库切换。

## journal 尾部中断

操作锁下追加状态时，会验证已有完整记录。仅最后换行后未完成的半条记录可以截掉再追加；完整坏 JSON、无有效完整状态的非空文件或大小上限超出会报错。保留完整历史，不用跳过损坏记录制造可读状态。`status` 仍可读取最后一条完整记录，操作错误和日志错误必须分别检查。

## 验证边界

本地回归覆盖临时 SQLite 的备份后写入、文件系统 journal、状态机、Docker 命令参数和实际工作流 shell 的隔离替身。它们不是实际 Docker部署、CI执行、远端磁盘故障恢复或线上业务验收。执行证据见 `docs/testing/bug-fix-durability-2026-10-10.md`。
