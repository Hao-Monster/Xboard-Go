# M0 多维审查报告

审查日期：2026-09-02
审查基准：`origin/main` at `b151f914fbf90fe5d341c5fd7caea7983799a66f`

## 结论

项目不是“七天没有进展”，而是在缺少版本化控制面的情况下高速堆叠了大量切片：实现覆盖广，但范围、证据、迁移和验收被混在同一个“完成”概念中。真正阻塞最快交付的不是单纯并发度，而是无法可靠判断子任务边界、依赖、当前证据和集成门禁。

M0 必须先恢复可知性，再扩大实现并发。否则并发只会增加共享文件冲突、重复验证和状态漂移。

## 审查维度与发现

| 维度 | 已验证事实 | 原缺口 | M0 处理 |

| 需求范围 | 本地资料含 80 个唯一需求 ID | 需求只在被忽略的 `docs-dev/`，公开仓库无法追踪变更 | 80 项完整进入 `requirements.json` 并由 CI 强制数量、唯一性和引用 |
| 完成度 | 历史审计为 76 implemented、2 partial、2 blocked | “实现”被误当成“已验证/已验收” | 拆为范围、实现、验证、迁移、验收五维；当前验收明确为 0/80 |

| 并发协作 | 取证、测试、安全审查可并行 | 共享迁移/API/路由/锁文件并发写会互相覆盖 | 单一集成责任人、共享面清单、按领域 Issue 和独立 PR 集成 |

## 特别保留的边界

- 不提交原始 `docs-dev/`。该目录可能含环境细节，且逐日记录不应重新成为权威需求。
- 不新增 CODEOWNERS。当前单一维护者场景下，强制所有者审批可能造成自我审批死锁；责任通过 Issue、里程碑和集成规则表达。
- 不启用 GitHub Projects。M0 用里程碑、Issue 和机器事实源已能建立控制面；看板不是当前阻塞点。
- 不把 6 个 Dependabot PR 直接合并。它们已归入 M3 并标记需要基于最新 `main` 重跑门禁。

## 剩余已知缺口

1. D-011、D-012、D-013 直接阻塞 `FIN-001`、`USER-001`、`USER-003`、`OPS-002`。
2. 其他 8 个待决策项影响 M2～M4 的数据库、客户端、沙箱、SLO、切换、视觉和 MFA 边界。
3. 80 个需求仍缺同一候选提交上的逐项当前证据与正式验收。
4. 代表性旧数据迁移、异地恢复、容量/SLO、供应链、发布/回滚仍未通过对应门禁。
5. 在 M0 PR 合并、治理检查加入主分支必需检查且精确 `main` 提交全部通过前，不创建首个预发布版本。
