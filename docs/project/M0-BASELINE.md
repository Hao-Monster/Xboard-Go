# M0 项目治理基线

基线日期：2026-09-02
基准提交：`b151f914fbf90fe5d341c5fd7caea7983799a66f`
环境边界：本地与隔离 CI/测试环境；不声明生产就绪

## 目标

M0 不重写业务功能。它解决项目无法可靠回答“完成了多少、还缺什么、什么证据有效、何时可发布”的控制问题，并阻止状态继续漂移。

多维审查证据和遗漏清单见 [`AUDIT-2026-09-02.md`](AUDIT-2026-09-02.md)。

## 第二轮审查补充

治理基线覆盖以下相互独立的维度：

- 范围：需求是否已决定，是否被业务决策阻塞。
- 实现：代码是已实现、部分实现、被阻塞还是未开始。
- 验证：证据属于当前候选提交、历史提交、部分验证还是没有证据。
- 迁移：旧数据/协议的迁移证据是当前、历史、部分、未评估或不适用。
- 验收：需求是否由当前证据正式接受。

另行纳入了此前容易漏掉的治理对象：完整 `D-001`～`D-018` 决策集、风险重开机制、兼容性例外、非功能/运维工作项、证据时效、共享文件集成责任、供应链风险和发布/回滚门禁。

## 已验证事实与初始状态

- 80 个功能需求 ID 均已分类。
- 历史审计称 76 项已实现、2 项部分实现、2 项被决策阻塞；这不是当前提交的逐项验收证据。
- 因此 M0 初始状态为：当前提交已验证 0/80，已验收 0/80。
- `USER-001`、`USER-003` 受 D-012 阻塞；`FIN-001` 受 D-011 阻塞；`OPS-002` 受 D-012/D-013 及运维证据阻塞。
- 原本标记为已解决的文档版本风险实际仍存在：`docs-dev/` 被 Git 忽略，不能提供公开仓库内的版本历史。本基线将其重新打开并用版本化事实源缓解。

## M0 范围

1. 版本化 JSON 事实源和自动生成状态页。
2. 可执行的模式、不变量、交叉引用和生成结果校验。
3. GitHub M0～M4 里程碑、工作项 Issue 和分类标签。
4. PR 元数据门禁、Issue 表单和项目级 Agent 规则。
5. 版本/发布、归档、安全报告和共享文件集成规则。
6. M0 合并后才允许创建首个非生产预发布 Tag/Release。

## M0 非目标

- 不替代 D-011、D-012、D-013 的用户业务决策。
- 不声称 76 个历史实现项已被当前 `main` 验收。
- 不合并 Dependabot PR，不重构现有长耗时测试，不部署任何环境。
- 不把本地 `docs-dev/` 原样提交到公开仓库。

## 可验证退出条件

- `go run ./cmd/projectctl check` 通过，并在 PR CI 中运行。
- 80 个需求、18 个决策、风险、兼容性例外、工作项和 M0～M4 门禁全部通过交叉引用校验。
- `docs/project/STATUS.md` 与机器事实源完全一致。
- 所有开放工作项有 GitHub Issue 和里程碑。
- PR 具备需求/工作项 ID、里程碑和关联 Issue。
- M0 PR 合并到 `main` 后，所有必需状态检查在该精确提交通过。
- 仅在上述条件成立后创建 `v0.1.0-alpha.0` annotated Tag 和 GitHub Pre-release；否则保持门禁阻塞并明确原因。

## 证据时效约束

- `requirements.json.baseline_commit` 是本轮验证目标，不是证据元数据提交对自身的循环引用。
- `current` 证据必须全部指向该目标提交，具有稳定证据/用例 ID、层级、环境和可核对产物，使用 RFC3339 观察时间且结果为 `pass`。
- 目标提交必须真实存在并是当前 `HEAD` 的祖先；治理 CI 使用完整 Git 历史验证该关系。
- `accepted` 还要求其引用的工作项全部完成；里程碑门禁负责在逐项验收后做聚合判断。
