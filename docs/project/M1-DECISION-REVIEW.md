## 3. D-011 建议决策

### 3.1 币种、金额和舍入

推荐：每个部署只允许一个结算币种，默认 `CNY`；一旦存在订单、支付尝试、余额或财务账本，币种代码不可通过普通设置修改。多币种不进入 M1。

- 所有金额存储为 `int64` 最小货币单位；M1 只支持两位小数币种。
- 外部十进制输入超过两位小数时拒绝，不截断。
- 支付百分比手续费按现有规则四舍五入到分；固定手续费在舍入后相加。
- 佣金比例分配保持向下取整到分；各级尾差不凭空入账。
- 所有请求和账本保存币种快照，不能从后来修改的显示设置反推历史币种。

替代方案是正式支持多币种。它需要为订单、余额、佣金、套餐价格、支付配置和对账全部增加币种维度，不是 M1 的低风险扩展。

### 3.2 提现账本

推荐保持已验证旧请求面的业务意图：用户选择允许的提现方式并填写收款账户，每次申请冻结提交时的全部可提现佣金，不增加任意金额输入。

- 提交事务同时创建申请、记录金额/币种/费率/方式快照，并将可用佣金转入冻结余额。
- 每个用户最多一个活动申请；客户端幂等键重复提交时返回原申请。
- 状态只允许 `pending -> approved -> paid`、`pending -> rejected`、`approved -> rejected`。
- `rejected` 必须在同一事务中只退回一次冻结金额；`paid` 不允许回退。
- 批准、拒绝和支付均要求管理员权限、revision CAS、二次确认和追加式审计。
- 标记 `paid` 必须提供有界、唯一的外部参考号；提现账户加密保存，列表、日志和审计只显示脱敏值。
- M1 不收取提现手续费；申请快照明确记录费率和费用为 `0`、净额等于冻结金额。客户端不得再显示硬编码的 1% 费率；未来收费必须新增业务决策和迁移方案。
- 工单可以承载沟通，但不能成为资金事实源。

不采纳“仅创建工单、不冻结余额”的兼容方案，因为它已证明会允许重复提现。

### 3.3 税费、退款、冲正和保留

推荐的 M1 范围：

- 系统不自动计算、代扣或申报税费，M1 不新增税额字段；若运营需要税务行为，必须作为新决策和新需求处理。
- 待支付订单取消继续按现有事务规则退回内部余额。
- M1 不开放已支付订单的自动退款 API；后续退款必须新增追加式退款账本，不得改写原支付和已完成订单事实。
- 支付 chargeback 或人工冲正必须是独立的正反向账务事件，引用原事件并保持总账可追溯。
- 在司法辖区和运营保留期得到正式确认前，订单、支付、佣金、提现、退款和冲正事实不自动删除；90 天日志 TTL 不适用于财务账本。

### 3.4 D-011 验收标准

1. Given 同一用户并发或重复提交提现，When 请求使用相同或不同幂等键到达，Then 只冻结一次且最多存在一个活动申请。
2. Given 可用佣金为 X，When 申请成功，Then 可用佣金减少 X、冻结佣金增加 X、总额守恒。
3. Given `pending` 或 `approved` 申请，When 管理员拒绝，Then 冻结金额只退回一次；重试不重复入账。
4. Given `approved` 申请，When 使用唯一外部参考号标记支付，Then 状态成为 `paid`，后续拒绝或回退失败关闭。
5. Given 配置币种与支付币种不一致，When 创建 checkout 或处理 webhook，Then 请求失败且订单、余额和账本均不改变。
6. Given 任意财务变更，Then 金额、币种、操作者、时间、幂等键、前后状态和关联事件可审计，敏感账户不进入日志。

## 4. D-012 建议决策

### 4.1 生命周期与权限

推荐保留 `banned` 作为可逆的安全/运营封禁，并新增独立生命周期：

`active -> pending_deletion -> anonymized`

- 只有管理员可发起或恢复；到期匿名化只能由受信的有界后台任务执行。当前管理员不能处理自己的账号。
- `account_kind != human`、存在未结算或活动分销责任、会导致系统失去最后一个有效管理员，或命中保留锁的账号失败关闭。
- 发起前必须读取影响预检并用最新 revision 二次确认；预检至少包含订单、支付/佣金/提现、分销订阅、邀请关系、工单/消息、附件和审计数量。
- 进入 `pending_deletion` 后立即拒绝登录和订阅访问，撤销所有会话、访问令牌、验证码、登录链接、订阅 token、Telegram 绑定和待发通知，并清理在线/设备状态。
- 管理员可在 30 天内恢复；恢复不复活旧 token，用户必须重新设置密码或由管理员安全重置凭据。
- 到期匿名化由有界、可重入任务执行；相同任务重复运行结果一致。

替代方案是确认后立即匿名化且不可恢复。它降低个人数据暴露窗口，但误操作没有恢复路径。普通硬删除不作为可选方案。

### 4.2 匿名化与保留矩阵

| 数据 | 到期处理 |
| --- | --- |
| 用户主键和墓碑状态 | 保留稳定 ID、匿名化时间和最小审计元数据 |
| 邮箱、密码、UUID、订阅 token、Telegram、备注 | 清除或替换为不可反推且满足唯一约束的墓碑值 |
| 会话、访问令牌、验证码、登录链接、在线/设备状态 | 在进入 `pending_deletion` 时撤销或删除 |
| 订单、支付、余额、佣金、提现、退款/冲正 | 保留业务事实和用户墓碑引用，不保留可选展示型个人信息 |
| 分销、邀请和权益事实 | 保留结算与归属事实；匿名化后不再允许新增责任 |
| 工单、消息、审计 | 保留业务与安全事实，界面只展示墓碑身份；正文中可能存在的个人信息纳入 D-013 保留/脱敏策略 |
| 附件和邮件正文 | 不由用户主表匿名化静默删除；按照 D-013/OPS-002 的独立保留策略处理 |

### 4.3 D-012 验收标准

1. Given 有受保护业务数据的用户，When 管理员发起删除，Then 影响预检准确展示关联数量且不硬删业务事实。
2. Given revision 已过期、当前管理员自身、内部账号或活动分销责任，When 发起删除，Then 失败关闭且无部分状态变化。
3. Given 删除已确认，When 事务提交，Then 账号立即不可登录/订阅，全部凭据与运行态被撤销，业务事实仍完整。
4. Given 仍在 30 天窗口，When 管理员用当前 revision 恢复，Then 账号回到 `active`，旧 token 仍无效并产生审计记录。
5. Given 窗口已过，When 到期任务并发或重复执行，Then 只匿名化一次；唯一约束、外键和财务守恒保持有效。
6. Given 已匿名化用户，When 查询订单、佣金、分销、工单或审计，Then 仍可追溯到稳定墓碑 ID，但普通界面和 API 不泄露原身份。

## 5. 已采用的最快可控执行拆分

决策确认是唯一串行门禁。确认后，FUNC-001 与 FUNC-002 按下列轨道推进；共享 schema 和最终集成由单一责任面串行收口，避免并发覆盖。

| 轨道 | 产物 | 依赖 | 主要文件所有权 | 完成门禁 |
| --- | --- | --- | --- | --- |
| FIN-A | schema、账本与状态机、迁移/回滚测试 | D-011 | `internal/store/` | 资金守恒、并发、幂等测试 |
| FIN-B | 用户/管理员 API、授权、敏感字段脱敏 | FIN-A 契约 | `internal/httpapi/` | API/权限/错误契约测试 |
| FIN-C | 用户申请与管理员处理 UI | FIN-B 契约 | `web/src/features/` | 组件、桌面/移动浏览器测试 |
| USER-A | 生命周期 schema、预检、停用/恢复/匿名化事务 | D-012 | `internal/store/` | 外键、CAS、重入、回滚测试 |
| USER-B | 管理 API、授权、运行态撤销 | USER-A 契约 | `internal/httpapi/` | 权限、会话、订阅访问测试 |
| USER-C | 影响预检、二次确认、恢复 UI | USER-B 契约 | `web/src/features/users/` | 组件、键盘、移动端浏览器测试 |
| QA | 独立资金/权限/数据保留缺口审查 | 两条轨道候选提交 | 测试与治理证据 | 无 Critical/High；精确提交证据 |

共享 `internal/store/sqlite.go` 的 schema 变更不能由 FIN-A 与 USER-A 同时直接写入同一工作树；应预先分配连续 schema 版本或由集成人统一落地，避免并发覆盖。

## 6. 已确认的业务决策集

1. D-011：是否采用单部署单币种、两位小数整数分、本文舍入规则；现有财务数据存在后禁止普通币种修改。
2. D-011：是否采用“冻结提交时全部可提现佣金”、两步批准/支付和拒绝原子退回；不采用仅工单方案。
3. D-011：M1 是否明确不自动计算税费、不开放已支付订单自动退款，财务事实在正式期限确定前不自动删除。
4. D-012：是否采用独立删除生命周期、30 天管理员恢复窗口、到期匿名化墓碑和普通硬删除禁用。
5. D-012：是否采用本文保留矩阵；工单正文、附件和邮件内容的期限继续由 D-013/OPS-002 决定。

上述五项已由用户在 2026-09-02 以 `确认开发：采用 M1 决策审查 v0.1 的 1-5 项推荐方案。` 明确确认；后续实现不得静默改变这些业务语义。
