## 一 目标与交接材料

管理员从仪表盘进入日志中心，输入完整订单号，系统自动解析实际订阅客户，展示客户日志 ID，再按节点、时间、域名、错误及精确 trace 查询连接，展开节点内部调用链、实际 DNS、失败原因和有来源说明的异常堆栈。已有客户日志 ID 可直接只读查询，租约操作仍需绑定订单。普通与分销订单快捷入口使用同一中心，无需手工查 UUID 或逐台 SSH 搜日志。

先读 [详细设计](customer-connection-diagnostics.md)，再使用 [开发提示词](../handoffs/customer-connection-diagnostics-developer-prompt.md)。详细设计定义协议与行为，本任务书定义实施顺序与交付证据。发生冲突时提交给技术负责人，不自行改变身份算法、租约顺序或部署边界。

交接已补齐 Dashboard 入口、精确订单 lookup、trace/span、异常栈来源、试点容量与迁移方案。没有业务实现、性能测试、真实节点接入或新日志试点部署的完成结论。此前开发机已有运维日志容器，不等于本功能已部署。

### D0 接手与保护

读取各仓库适用 AGENTS.md，记录 HEAD、工作分支、远端关系、子模块和未提交文件；辨认本任务文件与他人工作。检查本地 PHP、Node、Go、Linux/Docker 和浏览器测试能力，只运行隔离合成数据，不连接真实订阅或复制生产数据库。测试环境缺失时报告准确阻塞并继续独立工作，不能转用共享开发服务器或生产节点充当未授权测试环境。

交付 `docs/handoffs/customer-connection-diagnostics-progress.md`，包含基线、文件归属、任务状态、阻塞、review SHA 和证据索引。先列测试矩阵和数据范围，再编写实现。该进度文件由实施人员新建并维护，本次交接尚无实施进度文件。

### D1 契约与样本

详细设计中的 diagnostic_id、panel_scope、event_id、trace/span、字段长度、事件类别、safe_message 和完整租约快照是共同契约。将其做成可机读 schema 与跨语言合成 fixtures，放在 Xboardme 的 `tests/Fixtures/Diagnostics/`；节点测试复制同一已审核 fixture 并记录摘要，运行时不读取另一个仓库的本地绝对路径。

至少覆盖普通/分销/续费身份、相似订单号、scope 缺失、UUID 轮换、三个事件类别、共享 DNS link、边界栈、Unicode 截断、乱序快照。所有 ID 与日志为合成数据，不带真实 UUID、订阅 token 或客户源 IP。交付协议差异表、合法与非法样本、PHP/Go 两端断言。接口变化先同步设计和技术负责人，不能各自增加不同字段。

### D2 面板身份与同步

实现唯一 OrderDiagnosticIdentityService；分销首单和续费取 subscriber，缺失返回 409，绝不回退到分销商。lookup 精确匹配完整订单号或内部 ID，响应不含 UUID、token、订阅 URL。scope 在既有设置中显式初始化，唯一约束处理并发，普通读取不能生成临时 scope。

HTTP、WS 全量、分组及增量同步均加入可选诊断身份，复用现有认证和 owner 边界。不能只修改 HTTP 路径，也不能使未升级节点失效。交付实际路由 Feature 测试与 full/delta 对照证据。

### D3 节点元数据与兼容

同步更新 panel DTO、UserSpec、两个转换方向、用户合并及能力声明。HTTP、WS full、直接 delta、邮箱合并 delta 均在业务 hash 提前返回之前处理诊断映射；纯诊断变化不调用 limiter.UpdateUsers 或内核用户变更/Reload。删除、撤权、UUID 轮换及原有强制关闭照常生效，冻结的只是连接日志归属。交付兼容、热更新、撤权及重载测试。

### D4 节点观测

D4.1 在鉴权后的真实路由入口建立上下文，早于可能失败的 DNS/路由步骤，保持业务顺序。TCP 多路复用子流各自关联，UDP 保持有界 target_id 与逐出摘要；root/子 span 按真实调用形成，实际 relay 有结果事件。子操作失败只结束自身 span，最终连接终止才结束 root；重试成功不能继承错误的提前关闭。不能只改日志级别、抓普通文本或用图替代埋点。

D4.2 每个调用者有独立 DNS 结果；缓存不持有客户身份；共享操作有独立 trace 和 baseline exchange 结束摘要，客户结果单向引用。实际解析器来自执行点，未解析如实显示，客户端 DNS 为未知。以两个客户同域名、失败重试成功、缓存命中和后台刷新验证归属及生命周期。

D4.3 统一错误分类；有效 detail 租约下首次失败在原 goroutine 捕获栈，区分创建点、库原有栈、观测边界和不可用。保持 error、errors.Is/As 和 panic 行为；禁止在 sink 抓栈冒充源栈。事件含换行最多 4096 字节，栈最多十二帧/2048 序列化字节；超限先删栈及可选字段，必要时输出仍符合 schema 的最小错误摘要。baseline 错误附栈不降优先级，sidecar 序列化后释放。队列 2048 条/8 MiB、错误预留四分之一，输出阻塞不阻塞代理，健康可走控制面。

交付真实内核受控 TCP/UDP/DNS 测试、身份负面用例、内核重载回归及变更前后性能原始结果。不能用复制核心逻辑的测试替代真实依赖路径。

### D5 诊断租约

实现全局 control_epoch/control_version、Redis TIME、完整每节点快照、请求 ID、ACK、停止墓碑、幂等及单调截止。WS 只通知，ACK 验证当前 owner；REST 的 V1 legacy 与 V2 machine 两组 snapshot/ack 复用服务，后者强制 machine_id 且禁止降级，验证 machine 对节点的归属。保留 legacy 共享 token 既有范围，不虚称每节点隔离。

REST ACK 绑定最近已发快照的认证主体、transport、request_id、runtime、epoch/version，六十秒过期；不 claim 业务 WS owner，有 WS owner 时仅允许已登记 runtime 后备，旧 ACK 不登记新 runtime。所有 detail 发出时检查租约；长连接和共享 DNS 不越期，停止未确认显示 stopping。接通 D6.3 的私有 health：新建租约前一秒内校验 ready，失败拒绝新建；stop 不依赖该接口。交付双鉴权、乱序、重连、跨 session、Redis 丢状态、时钟偏差和恢复测试。

### D6 日志采集与试点保护

D6.1 在 Xboardme 的 `deploy/diagnostics/` 建立配置生成器，参考 Xboard-Go 实现，禁止修改它的共享运行配置或工作流。提供固定摘要镜像清单、逐类别白名单、event_time 规则、每节点写入身份覆盖、面板只读身份和独立 2 GiB 缓冲。正文、重复 query 和 header 伪造都必须被拒绝或覆盖成受信任身份。

D6.2 生成独立 Compose、挂载服务及预检配置：30 GiB 真实预分配文件系统、三天保留、20 GiB 清理、5 GiB 紧急保护，新库一个 CPU/1.5 GiB 内存。已有目标、错误文件系统和挂载缺失拒绝执行；禁止落回根盘目录。新库启动重启均受挂载检查控制。实际共享主机的创建或格式化不是本地开发任务。

D6.3 实现单一轻量 guard：vmauth 认证后写入经 guard 转发，查询绕过写入门禁；guard 退出时上游返回 5xx。三十秒检查、每请求核验六十秒新鲜度，16 GiB 预警、24 GiB/6 GiB 停收、根盘 `max(50 GiB,20%)`、持久锁存与显式恢复。提供经鉴权只读 GET /diagnostics/health，供 D5 新租约检查和界面展示；状态保存在独立 state/，不依赖故障库。容量阈值与已证实历史被删分开；完整缓冲为 delayed、已知缺口为 partial、不确定为 unknown。验证 guard 退出、陈旧状态、网络失败、新建拒绝而 stop 可用，不增加另一套队列或 watchdog。

交付生成配置、隔离环境可重复验收脚本及保护故障报告。所有生产地址与凭据使用参数或受保护配置引用；测试使用假的服务和独立测试凭据。

### D7 查询与日志中心

D7.1 每次验证管理员、服务端 scope 和客户范围；订单模式重新解析 subscriber，日志 ID 模式仅只读、不反查哈希或新增映射表。精确 trace 筛选下推后再执行读取预算。连接及 DNS 展开共用一万条/16 MiB、五秒总时限，详情合计一千条/2 MiB，每页最多三十二个授权操作 ID 批量展开，禁止 N+1。实现累计错误、目标聚合、受控快照游标与 coverage，游标绑定查询方式和 storage_generation；首期只有一个可配置查询端点。诊断 error.code 沿用现有外层响应，不改全局 ApiResponse；拒绝原始 LogsQL，日志失败不拖垮订单接口。

D7.2 在 `/<secure_path>/#/?diagnostics=1` 提供中心，普通/分销快捷按钮只传 order_id。支持完整订单号或已有日志 ID 只读查询、精确 trace 筛选；ID 模式显示未绑定订单并禁止租约操作。展示身份卡、列表、调用链、DNS、栈及观测缺口。菜单幂等，离开页面停止诊断轮询，切客户/方式取消旧请求，认证失效清空，日志按文本渲染。保留 Dashboard 原有轮询；浏览器验证桌面/窄屏、主题、刷新/后退、相似订单号及原有功能。

D7.3 为后续迁移准备，本期不实施、不阻塞 D8/P1。P1 报告后、P2 之前再开发双源和转发：两源及 DNS 共用总预算，每源五千条/8 MiB，按 event_id 去重，storage_generation 使旧游标失效；任一源失败不报完整。在两个隔离库完成 T20，演练唯一实际写入目标、旧入口转发、缓冲保留、迟到重试和回切，防止循环或身份丢失。首期仅交付 M1–M7 手册及稳定端点配置，不提前实现整套迁移控制。

每个里程碑提交证据供技术负责人审查。普通实现选择无需反复请求用户批准；未决协议、身份归属、权限或业务语义变更必须先交技术负责人裁决，期间可继续不依赖该问题的工作。代码未经过独立 review，不标记为验收完成。技术负责人不代替用户批准部署。

## 五 测试与证据要求

先制定可执行测试用例，再实现。使用合成订单、客户、DNS 与目标服务。单元测试负责规则，真实框架路由负责鉴权，真实内核负责 TCP/UDP/DNS，隔离 Linux journald/Vector/VictoriaLogs 负责采集存储，真实浏览器负责页面交互。分别记录这些层次，不能以 Mock、healthz 或容器 running 代替真实验收。

Xboardme 候选执行完整 PHPUnit、JavaScript、PHPStan、Composer audit、现有部署脚本语法与工作流校验、git diff --check。Xboard-Node 按自身规则执行 internal 测试、Linux race、vet、gofmt、govulncheck、Linux amd64/arm64 和镜像构建，以及安装脚本语法和制品校验测试。不修改工作流也要验证它未被破坏。

数据面必须比较相同条件下的原基线、baseline 观测、detail 三组，覆盖成功及高频失败抓栈负载；baseline 吞吐下降预算不超过百分之五，连接建立 P95 增量不超过五毫秒。日志试点目标及磁盘计算另按详细设计验收，不能从本地跑分直接声称开发服务器容量足够。

T19 当前为 NOT RUN，原因“未获试点部署授权”；T20 为 NOT RUN，原因“后续 D7.3 迁移阶段”，不是首期失败或遗漏。T17/T18 隔离通过后在 P1 现场核验，T20 后续隔离通过后在 P2 核验。新代码使旧测试失败须修复，旧基线失败须附原基线复现，不能无证据归为历史问题。

## 七 停止边界

遇到需要改流水线、重置工作区、修改未知迁移、操作真实数据库、重启生产节点、创建共享服务器卷、配置真实凭据或上线新服务时，停止该动作并报告技术负责人；继续其他本地开发。不得通过关闭设备限制、放开认证、删除日志或改计费规避测试失败。

开发测试服务器已经选为试点目标，但本任务书未批准任何服务器部署。不存在“开发完成自动上线”“定时自行上线”或“技术负责人 review 通过即获得部署授权”的规则。
